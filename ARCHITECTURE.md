# ARCHITECTURE.md — модули и интерфейсы

Проектирование интерфейсов до содержимого — единственное, что делает параллельную работу возможной и позволяет переписывать любой модуль, не трогая соседей.

---

## Золотое правило

**Каждый модуль — функция от среза журнала.**

```
module(journal_slice, state) -> (output, new_state)
```

Отсюда следует всё остальное: любой модуль тестируется офлайн на записанном корпусе без запуска игры, две версии сравниваются на одних данных, а воспроизводимость получается бесплатно.

Модуль, который нельзя прогнать по записи, спроектирован неправильно.

─────────────────────────────────────────────────────────────────

beliefs/     конвейер, происхождение, deferred       М4
sleep/       консолидация, вытеснение, сновидение    М4, М8

## Контракты данных

Заморозить до написания содержимого модулей.

### Запись журнала

```
TraceRecord {
  t_self: int              # цикл восприятия агента
  t_world: int             # тик мира
  t_content: int | null    # время внутри просматриваемого содержимого
  wall_clock: float        # якорь реального времени

  profile_hash: str
  lineage_id: str
  branch_id: str

  actor_layer: enum        # reflex | skill | planner | drive | interrupt | human | none
  action: Action | null
  stated_reason_id: str | null

  prediction_error: float
  drives: dict             # значение и прогноз по каждому
  mood: (valence, arousal)
  goal_id: str | null
  goal_transition: enum | null

  segment_ref: SegmentRef | null   # может указывать на понижённый сегмент
}
```

### Действие

```
Action {
  keys: list[ScanCode]
  duration_ms: int
  modifiers: set[ScanCode]
  mouse_delta: (dx, dy) | null
}
```

Никогда не дискретное событие. Длительность — ось, а не свойство.

### Восприятие

```
Percept {
  t_self: int
  screen_mask: Mask              # что прибито к экрану
  world_mask: Mask
  entities: list[EntityObservation]   # отпечаток, положение в кадре, слой
  symbols: list[SymbolObservation]    # SYM_*, область, пространство имён
  sound_bearings: list[(bearing, signature)]
  flow: FlowField                # оптический поток, для параллакса и tau
  focus_windows: list[Rect]      # куда смотрело внимание и почём
}
```

Из `Percept` **не должно быть возможности** восстановить координаты, имена или разметку. Это проверяется тестом инварианта 4.

### Карта действий

```
ActionMap {
  live: dict[ScanCode, EffectClass]   # axis|locomotion|mode|impulse|modifier|contextual
  silent: set[ScanCode]
  combos: list[(modifier, key, EffectClass, confidence)]
  reversibility: dict[ActionSignature, (mu, sigma, n)]
  context_conditioned: bool           # эффект зависит от класса состояния
}
```

### Карточка и убеждение

```
Entity {
  id, kind, fingerprint, agent_label: SymbolRef | null
  encounters: list[EpisodeRef]
  affordances: list[Affordance]     # действие, результат, mu, sigma, n, reversibility
  dynamics: list[Observation]
  relations: list[(RelationType, EntityId, confidence)]
  rank, last_access
}

RelationType = at | part_of | causes | resembles | precedes | represents

Belief {
  claim, provenance, source_ref
  mu, sigma, n
  episode_refs: list[EpisodeRef]
  state: verified | refuted | deferred
  test: TestSpec | null             # null => это вопрос, не гипотеза
}
```

`test == null` — формальный признак вопроса. Не отдельный тип, а отсутствие конструируемой проверки.

### Цель

```
Goal {
  statement, source: drive | curiosity | testimony
  satisfaction_test: TestSpec
  budget, spent, remaining_estimate, sigma
  expires_at
  state: proposed | active | suspended | abandoned | satisfied
  saved_context                     # для возврата после прерывания
}
```

Цель без `satisfaction_test` не создаётся. Это отсекает дрейф на длинных задачах в момент постановки.

## Поток данных

```
harness.capture ──Frame──> perception ──Percept──┐
                                                  ├──> world ──WorldState──> control
body.action_map ──────────────────────────────────┘                            │
                                                                               │
drives + goals ────────────────────────────────────────────────────────────────┤
                                                                               ↓
                                             gate ←──ActionRequest── control.arbitrate
                                              │
                                              ↓
                                       harness.inject

           всё вышеперечисленное ──────> journal (дозапись)
```

Ключевое: **`control` не вызывает `inject` напрямую.** Между ними `gate`. Даже когда шлюз пропускает всё, путь один — иначе однажды кто-то добавит обход.

## Правила модулей

**`perception` не знает, что такое игра.** Никаких имён, никаких специальных случаев. Если код содержит слово `minecraft`, он в неправильном месте.

**`body` не знает названий клавиш.** Только скан-коды и наблюдаемые эффекты.

**`beliefs` не создаёт утверждений сам.** Только принимает с происхождением.

**`control` не форматирует объяснений.** Оно отдаёт `stated_reason_id`, ссылку на реплику. Сопоставление объяснения с `actor_layer` — работа метрик, а не контроллера.

**`gate` не использует модель.** Только механические признаки: метод запроса, тип элемента, домен. Тупой и неподкупный.

**`debug` пишется, но не читается агентским кодом.** Тест: собрать агента без `debug/` в путях импорта — он должен работать.

## Решение: профиль не делится по источнику (TASK-09, часть 4)

В живой сессии с `source: screen_dxcam` лежат `world_bounded`, `world_variable_cost`,
`world_cost_jitter`, `world_extent_px`, `randomize_world` — настройки, которые может
прочитать только синтетический мир. Задача предлагала рассмотреть разделение профиля по
применимости к источнику.

**Решение: не делить.** Причины, по убыванию веса:

1. **`profile_hash` — идентичность эксперимента.** Если из живого профиля выбрасывать
   ключи, хеш в разных сессиях считается по разным словарям и перестаёт быть сравнимым.
   Два прогона с одинаковыми настройками получили бы разные хеши только потому, что
   один живой, а другой синтетический.
2. **Запись обязана описывать себя.** По профилю с выброшенными ключами нельзя
   отличить «этой настройки тогда не существовало» от «эта настройка была
   неприменима». Первое — история схемы, второе — свойство источника, и путать их
   значит терять возможность прочитать старую запись правильно.
3. **Два вида профиля — это два механизма под одним именем.** Тот самый третий исход
   из `AUDIT.md`, которого мы уже избегали дважды.

**Вред, который задача называет** — ложные различия при сверке двух живых профилей, —
снят подписью, а не выбрасыванием. Применимость объявлена при настройке
(`Setting.applies_to`) или при её группе (`settings.GROUP_APPLIES`), `settings.applies_of`
сводит одно с другим, а `Profile.diff` помечает каждую строку полем `live`.
`Profile.live_diff` оставляет только те различия, которые могли повлиять на живую запись.
`settings.SYNTHETIC_ONLY` теперь **выводится** из этих объявлений, а не перечисляется
рядом: ручной список из семи имён был вторым местом правды и мог разойтись со схемой
молча — добавив настройку мира, легко забыть дописать её туда.

## Мёртвые параметры и заявления записи о себе (TASK-10)

Два механизма, оба выросли из одного случая: живая запись несла профиль, заявляющий кадр
в 36 раз меньше настоящего.

**`harness/params.py` — детектор параметров (инвариант 30).** Перечисляет все настройки
схемы и для каждой устанавливает читателей двумя способами: статическим обходом AST
(`read_sites` — знает модуль, функцию и обслуживаемые пути) и счётчиками обращений в
прогоне (`counting_profile`, `runtime_probe` — видят чтение по вычисленному ключу).
Диагноз ставит статика: однобокость есть свойство путей, и счётчиком не устанавливается.
Пять диагнозов, отсортированных по тяжести: `однобокий` (опаснее мёртвого — выглядит
работающим), `мёртвый`, `только отчёт`, `задел`, `работает`. Команда: `harness params
[--all] [--run]`, ненулевой код возврата при найденных дефектах. Число дефектов идёт в
постоянные показатели (`vitals.params_defective`) — оно не должно расти незамеченным.

**`session.RECORD_CLAIMS` — поля профиля, описывающие свойство самой записи.** Каждое
сверяется с записью, и расхождение — отказ, а не предупреждение: размер и формат кадра на
первом кадре (`Recorder._check_declared`), число каналов звука на первом блоке
(`AudioStore.append_block`), частота дискретизации при открытии устройства
(`LoopbackAudio.start`). `capture_fps` в список намеренно не входит: частота кадров —
цель для цикла, а не свойство записи, машина с 28 кадрами вместо тридцати работает
нормально, а достигнутая частота наблюдаема по трём часам самой записи.

## Конвейер убеждений и сон (TASK-12)

**`model/beliefs.py` — четыре положения, три перехода.** `State` отвечает на «чем
кончилось» (три исхода, `None` у гипотезы в работе), `Stage` — на «где она сейчас» (четыре
положения, перечислимы). Две сущности, а не одна, и сводить их нельзя ни в какую сторону:
выдать гипотезе в работе `deferred` значит смешать перечень непонятого с очередью дел,
выдать отложенной `hypothesis` — утверждать, что проверка существует. Переходы объявлены в
`TRANSITIONS`, обратных нет ни одного, у каждого счётчик (`pipeline_arbitration`,
инвариант 26).

**Происхождение не повышается у пересказа.** `hunch` → `experience` при собственной
проверке — законно, догадка была своя. `testimony` → `experience` — **никогда**: своя
проверка пишется в `Belief.checked_at` и растит `n_experience`, но метка происхождения
остаётся. На этом различении стоит вся защита от загрязнения, и оно должно переживать
подтверждение.

**`model/questions.py` — реестр отложенного.** У вопроса хранится не только «почему теста
нет», но и **чего не хватает** (`reopens_on`, закрытый словарь `Missing`). При изменении
множества доступного реестр предлагает построить тест и уважает отказ: доля отказов и есть
доля ложных срабатываний этой проверки, а доля вопросов, объявивших нехватку, — её
покрытие (инвариант 31). Жизнь вопроса пишется записью `HYPOTHESIS`, поэтому перечень
непонятого выводим из журнала (инвариант 1).

**`model/bookmarks.py` — закладки и карантин (инвариант 18).** Закладка ограничена
(`bookmarks_per_sleep`), протухает к следующему сну, требует причины и продления с заново
названной причиной. Карантинный класс — смерти, всплески ошибки, рост конфабуляции,
отметки оператора — агенту недоступен: `may_demote` отказывает и записывает отказ.
Понижение идёт только через `demotable`, иначе обошло бы и закладки, и карантин.

**`model/consolidation.py` — полный набор операций сна** (`SLEEP_OPERATIONS`): слияние и
расщепление, пересчёт `mu`/`sigma`, добыча скриптов, ранжирование, понижение. Каждая
докладывает число, и **ноль докладывается тоже**: сон без графа печатает «рёбер
пересчитано 0», а граф без `recompute()` даёт отказ, а не молчаливый ноль. Реконсолидация
— `BeliefStore.recall`: извлечение есть транзакция, растит обращения и ранг, но `mu` не
двигает (извлечение — не наблюдение). Дрейф памяти (`rebuild.drift`) — доля утверждений,
по которым живое хранилище расходится с пересобранным из журнала.

## Карточки и тождество (TASK-14)

**Одна структура на все виды.** `Entity` — карточка места, предмета, другого, звука,
состояния и мысли; вид лежит в `kind` (`EntityKind`, набор закрыт). Отдельный класс на
каждый вид сделал бы карточки несравнимыми, а сравнение — это то, из чего берутся
категории: слот в игре и поле для перетаскивания в редакторе попадают в один кластер
именно потому, что у них одинаковая сигнатура аффордансов.

**Связи типизированы** (`Relation`, девять типов), и три из них — про происхождение:
`made_by`, `used_by`, `found_with`. `found_with` есть честная позиция «связь наблюдаю,
причину нет», и приписать `made_by` вместо неё значит выдать вывод за наблюдение.

**Тождество провизорно.** Карточка не «есть» сущность, а «пока считается» ею:
`identity_confidence` падает при каждом пересмотре, `identity_note` говорит, откуда
карточка взялась. Пересмотр — во сне (`model.identity.revise`), когда накопилось
свидетельство: в момент встречи свидетельства ещё нет, и решать тождество по одному
наблюдению значит решать монеткой.

**Слияние требует свидетельства, а не похожести.** Общий отпечаток либо близкий (о
близости спрашивается у источника отпечатков — это его свойство, а не механики).
Похожесть аффордансов даёт **категорию** (`propose_categories`), и это разные вещи: пока
похожесть считалась тождеством, шесть сущностей склеивались в две, и ошибка росла с нуля
до четырёх (`MEASUREMENT.md`, раздел 23).

**Расщепление задним числом** делит карточку по эпизодам: `Entity.sightings` держит
встречи поштучно, каждая знает свой номер записи и исход. Убеждения половин
пересчитываются из их встреч, ссылки от других карточек разводятся по эпизоду. Наугад
разводить нельзя: ссылка, отданная не той половине, добавляет третью ошибку поверх
исправляемой.

**Функция отпечатка заменяема** (`Fingerprinter`): механика тождества от неё не зависит и
прогоняется на двух источниках сразу. Если качество отпечатка поедет, менять придётся одну
функцию, а не слияние с расщеплением.

## Тест объявляет окружение (TASK-15)

**Два утверждения, которые были слиты, и разделены навсегда.** «Без графической сессии
код отказывает громко» — про поведение: проверяется **подменой** и обязано проходить на
любой машине. «На этой машине графической сессии нет» — свойство машины: предметом теста
быть не может вообще. Пять падений на машине оператора были ровно этой путаницей: тесты
сравнивали поведение с наличием `DISPLAY`, ждали отказа от установленного пакета и кода
возврата 2 от прошедшей записи.

**Подмена делается на `machine.detect`, а не на переменных окружения.** Удаление
`DISPLAY`/`WAYLAND_DISPLAY` подменой не является: на Windows этих переменных нет вовсе, и
сессия определяется по `platform.system()`. Тест, удаляющий переменные, там не меняет
ничего и продолжает проверять машину. `detect` — единственное место, где вся система
отвечает на вопрос «что это за машина», поэтому подменяется оно.

**Объявляющие фикстуры** (`tests/conftest.py`): `as_session` — какая графическая сессия,
`without_package` / `with_package` — установлен ли пакет захвата, `without_key` — задан ли
ключ к внешнему сервису (вторая ось: свойство настроек оператора, а не машины),
`requires_display` — пропустить там, где настоящего экрана нет. Пропуск честнее зелёного:
зелёное означало бы, что проверка прошла, а она не выполнялась.

**Фикстура возвращает машину, и брать надо её.** `as_session` подменяет `detect` в
`harness.machine` и в модулях, импортировавших имя, но тестовый модуль держит свою ссылку:
`detect()` в теле теста вернёт настоящую машину. Поэтому объявляющая фикстура **возвращает**
`Machine`, и пользоваться надо возвращённым значением — иначе подмена окажется частичной, а
тест снова начнёт зависеть от того, где идёт прогон.

**Правило проверяется механически** (`tests/test_environment_rules.py`): ни один тест не
читает окружение напрямую, и тест, трогающий захват или осмотр машины, объявляет окружение.
У проверки предъявлены доля ложных срабатываний по каждой редакции и покрытие (инвариант
31); обе первые редакции кричали в основном на своих, и это записано в её же докстринге.

**Двух инструментов нужно два.** Статический разбор видит форму и идёт на каждом прогоне;
замер (`tools/measure_env_dependence.py`, плагин `tools/envplug.py`) прогоняет весь набор в
пяти объявленных окружениях и видит смену исхода. Слепые пятна не перекрываются: тест с
утверждением под недостижимым условием зелен во всех окружениях сразу, и замер о нём молчит
устройством, а не по нехватке данных.

**Знание о Wayland живёт в одном месте.** `capture.select.NO_BACKEND` плюс `supported()` и
`why_unsupported()`; `machine.HAS_CAPTURE` удалён, `Machine.has_capture` спрашивает реестр,
`ScreenCapture.start` берёт причину отказа **строкой из реестра**. Копий было три, и
предыдущий заход поставил тест на их согласие, оставив копии, — то есть закрепил
расхождение вместо того, чтобы его убрать.

## Ход записи и прерывание (TASK-16)

**Ход записи — часть механизма, а не оформление вывода.** Единственный шаг проекта,
который может сделать только человек, не выполнялся из-за отсутствия обратной связи:
запись молчала минуту, и оператор прерывал её как зависшую. Поэтому `harness.progress`
живёт рядом с захватом, а не в разборе аргументов, и его настройки лежат в схеме.

**Печать хода меняет то, что записывается.** На записи «неподвижность» изменение экрана —
измеряемая величина, а мигающая строка в терминале попадает в кадр как изменение: при
30 кадр/с и обновлении раз в секунду это до 3.3 % оборотов. Отсюда `progress.FILE_KINDS`:
для таких видов ход идёт в файл рядом с сессией, а на экран печатается, куда смотреть.
Выбор объявлен и записан в журнал (`INTERVENTION` с кодом `progress`) — иначе вопрос
«почему здесь 3 % изменившихся кадров» останется без ответа.

**Строка собирается чистой функцией.** `Sample` — наблюдение, `render_line` — строка,
`Progress` — канал и частота. Разделение нужно не для красоты: без него ход записи
проверялся бы только глазами на машине с дисплеем, которой у разработки нет.

**Оценка остатка — по достигнутому темпу, доля — по оборотам.** `capture_fps` — цель для
цикла, а не свойство записи; на машине, отдающей 20 кадров вместо тридцати, оценка по
заявленной частоте врала бы в полтора раза ровно там, где оператор решает, ждать ли ему.

**Цикл записи вынут в `capture.record_loop`.** Он обязан проверяться офлайн, на поддельном
источнике кадров, и он же перехватывает `Ctrl+C` — **внутри** открытой сессии. Снаружи
поздно: `with Recorder(...)` закрывает хранилища на выходе, и записать отметку уже некуда.
Ровно поэтому отметки и не было.

**Прерывание — вмешательство человека, а не разрыв захвата.** `INTERVENTION` с кодом
`record_interrupted`, `Actor.HUMAN`, и в событии — на какой секунде из какой. `CAPTURE_GAP`
означает потерю кадров; здесь ничего не потеряно, и смешение сделало бы нажатие Ctrl+C
поломкой захвата в статистике. Отметка выводится из журнала (`Session.interrupted`), а не
хранится второй копией в `session.json`.

**Отказ по занятому каталогу осматривает каталог.** `session.describe_existing` различает
три случая — годная запись, прерванная запись, посторонние файлы — и даёт готовую команду
на свободный путь (`next_free_path`). Прежний отказ говорил «не пуст» на все три, и
оператор, прервавший запись, получал его как приговор своей записи.

**`verify` считает новые кадры и отметки раздельно.** Отметка «без изменений» ссылается на
уже лежащий блок и нового не добавляет; сравнение всех FRAME-записей с числом блоков
объявляло сломанной любую запись со статикой — в первую очередь «неподвижность», где
отметок больше, чем кадров (`MEASUREMENT.md`, раздел 25.2).

## Срок, стоимость кадра и пути (TASK-17)

**`--seconds` — срок, `--frames` — счёт кадров.** Два флага, два смысла, и растягивать
запись молча нельзя: `--seconds 10` превращалось в 300 кадров и на 6.5 кадр/с шло 46
секунд. Срок обрывает запись, недобор частоты печатается числом (`оборотов 40, ожидалось
60`), а `capture_fps` остаётся тем, чем был — целью цикла, а не свойством записи.

**Стоимость кадра разбирается по стадиям, и разбор снимается там, где идёт запись.**
`blobstore.Cost` считает разность, сжатие и запись в файл; `record_loop.Turns` — ожидание
кадра и время `Recorder`. Разбивка печатается в конце записи и ложится в журнал записью
`INTERVENTION` с кодом `cost`. Причина: живая запись дала 6.5 кадр/с против 32.5 у
`selftest` на одной машине, и «узкое место где-то в записи на диск» диагнозом не является.
Замер (`MEASUREMENT.md`, раздел 26) показал, что файл забирает 0.1–0.3 мс на кадр 1080p, а
дороги две вычислительные стадии в основном потоке.

**Разность кадров считается в uint8.** Арифметика uint8 в numpy переполняется по модулю 256
сама, то есть даёт ровно то же число, что запись через int16, одним обходом вместо четырёх:
14.9 → 0.5 мс на кадре 1080p. Тождественность проверена на всех 65536 парах значений —
выборочная проверка здесь означала бы кадры, расходящиеся при чтении в редких пикселях.

**Ход записи печатается по-разному в терминал и в перенаправленный поток.** В терминале —
возврат каретки с обрезкой по ширине окна; дополнение до фиксированных 96 столбцов
переносило строку в окне шириной 80, и обновление уходило поверх переноса. В
перенаправленном потоке возврат каретки не возвращает ничего, поэтому там печатаются
строки с переводом. Итоговую строку печатает **вызывающий**, и только он: `Progress.finish`
возвращает текст и не пишет его сам, иначе итог выходит дважды.

**Пути раскрываются и печатаются нами** (`harness.paths`). `cmd.exe` и `powershell` тильду
не раскрывают — это соглашение `sh`, — поэтому `~` доезжает до программы именем каталога, и
кто его не раскроет, тот его и создаст. На входе `resolve_input` раскрывает `~` и отказывает
на буквальном `~` в середине пути; на выходе `show` печатает форму целевой системы. Строка
для копирования обязана работать при вставке.

## Цикл записи: срок, частота, бюджет (TASK-18)

**Срок и предел оборотов не совмещаются.** При заданном `--seconds` предел не применяется
вовсе: иначе на неподвижном экране отметки «без изменений» набираются со скоростью
процессора, и минута кончается за секунду — так и вышло. Что считает предел, когда он
задан, объявлено в `record_loop.TURNS_MEAN`: обороты, то есть взгляды на экран, включая
отметки. Считать только изменившиеся кадры нельзя — запись неподвижного экрана тогда не
кончится никогда.

**Цикл держит целевую частоту.** Ожидание до начала следующего оборота считается по
расписанию **от старта**, а не «период после предыдущего»: второе накапливает отставание.
Дело не в сожжённом процессоре: без ожидания интервалы между кадрами случайны, а на них
стоят оптический поток, tau и все временные оценки — `t_world` в вехе 0 есть номер кадра.
Ожидание считается (`Turns.idle_ns`) и печатается долей.

**Узкое место объявляется по бюджету кадра**, а не сравнением стадий между собой
(`cost.verdict`). Бюджет — `1000 / capture_fps`. Сравнение стадий находило узкое место
всегда: у двух чисел одно непременно больше, и «ждал кадр 3.1, писал 0.8» объявлялось
узким местом при десятикратном запасе. Ожидание между оборотами в работу не входит.

**Стоимость кадра снимается на объявленном изменении экрана** (`harness cost`, `cost.scan`).
Стоимость зависит от того, насколько меняется кадр, на порядок: 4 КиБ у неподвижного экрана
против 58 КиБ у сдвинутого целиком и 2026 КиБ у шума. Поэтому две записи без указания доли
изменения несравнимы, и доля печатается в конце каждой записи. Размер кадра для замера
берётся **у экрана**, а не из профиля: в профиле 320×180 — размер синтетического мира.

**Верхняя граница подписана как граница.** Строка «шум» в таблице стоимости — не модель
экрана, а несжимаемый предел. Она нужна затем, что живой экран оператора сжимался почти
как шум, и без границы это число не с чем сравнить.

## Запись из панели (TASK-19)

**Записывать умеет один модуль, и его зовут двое.** `recording.record` — подготовка, прогон,
итог; ничего не печатает и ничего не решает за вызывающего: отказывает значением
(`RecordRefused`) и возвращает числа (`Outcome`). Печать — дело `cli.cmd_record`, показ —
дело сервера панели. Второй цикл записи в сервере разошёлся бы с первым через месяц, как
трижды разошлось знание о Wayland.

**Сервер — замена терминалу на одной машине, а не веб-сервис.** Отсюда четыре ограничения,
и каждое проверено:

- слушает только `127.0.0.1`; адрес — константа `HOST`, параметра для него нет;
- **пути в протоколе нет вовсе**. Куда писать, решает сервер по виду записи из
  `corpus.live.KINDS`; подделать нельзя то, чего не передают;
- запуск требует ключа, который сервер вставляет в отданную им страницу. Защита не от сети
  — в сеть сервер не смотрит, — а от другой вкладки того же браузера: без ключа любая
  открытая страница смогла бы начать запись экрана;
- отдаётся перечисленный список файлов, а не каталог: иначе раздавались бы и записи, и
  отладочный поток.

**Запись идёт потоком в этом же процессе.** Подпроцесс потребовал бы останавливать запись
сигналом, а `CTRL_C_EVENT` на Windows доставляется всей группе процессов и работает не
всегда. Поток останавливается флагом, и флаг ведёт в **тот же** `record_interrupted`, что и
`Ctrl+C`: два места нажатия — одно событие, «человек решил остановиться».

**Ход отдаётся опросом раз в секунду**, а не потоком событий: обновление и так идёт с
частотой `progress_min_interval_s`, а долгоживущее соединение добавило бы вторую точку
отказа. Числа в панели — **те же** наблюдения, что печатаются в терминал: панель
подписывается на `Progress.on_sample`, а не считает своё.

**Годность отделена от целостности.** `verify` отвечает, цела ли запись; `panelserver._usable`
— годна ли она для того, ради чего делалась. Запись неподвижности с нулём отметок «без
изменений» цела и бесполезна: она мерила мигающий курсор. Панель говорит это красным.

**Фикстура пересобирается после записи сама**, и пересборка не молчит ни в одном исходе.
Между записью и панелью стоял ручной запуск `tools/make_panel_fixture.py`, о котором
оператор не обязан помнить; пока он о нём не помнил, на первом экране был синтетический шум
вместо его рабочего стола. Молча оставить прежнюю фикстуру значило бы показывать чужую
запись под видом собственной.

**Панель, открытая файлом, говорит, что записывать нечем**, и называет команду. Кнопка,
которая ничего не делает, — обещание поведения, которого нет.

## Одно опорное число и обе границы из него (TASK-11, часть 1)

**«IoU на синтетике» было двумя разными величинами под одним именем.**
IoU 0.97, единица усреднения **генератор**, `n` = 1 — одиночный разделитель по параллаксу
на корпусе; маска истины побитово одинакова при любом сиде.
IoU 0.667, единица **домен**, `n` = 5 — арбитр трёх признаков по доменам.
Ожидание по живому было откалибровано против первого, а печаталось рядом со вторым; против
0.667 то же ожидание означало «ничего не изменится», против 0.97 — «серьёзный обвал». Одно и
то же число говорило два противоположных утверждения, и различить их было нечем, потому что
единица усреднения не публиковалась.

**Опорное число одно, и живёт в одном месте.** `corpus.live.synthetic_reference()` возвращает
не `float`, а запись: значение, статистику, единицу, `n` и разброс. Функция, отдающая одинокий
`float`, — ровно тот способ, которым число разошлось: получатель не знал, что получил.
`synthetic_text()` — единственная форма публикации; `harness record --plan`, `bench-live` и
`docs/STATUS.md` печатают её, а не свои копии числа.

**Медиана, а не среднее, — по замеру, не по вкусу.** Выброс `depth` (0.196) — домен, где
допущение «у мира одно движение» ломается нарочно. Без него медиана уезжает на +0.031,
среднее — на +0.092: среднее в три раза чувствительнее к одному домену из пяти.

**Единица — домен, и это установлено, а не выбрано** (инвариант 22). Разброс между доменами
sd 0.254 против разброса по сидам внутри домена sd 0.000–0.062: смена сида не добавляет
наблюдения, смена домена добавляет всё. Событий было 30, независимых единиц пять.

**Обе границы опровержения выведены, а не нарисованы.** Прежние 0.4 и 0.85 были числами из
прозы (инвариант 23), и оба стояли не там: 0.4 попадала **внутрь** разброса синтетики — два
домена из пяти дают меньше, то есть «метод не работает» объявлялось бы на значении, которое
сама синтетика выдаёт как норму, — а 0.85 стояла **выше** любого синтетического домена и не
отличала «подозрительно хорошо» от «как лучшая синтетика». Теперь:

- **пол** — тривиальный ответ «весь кадр — экранный слой», посчитанный по разметке той самой
  записи, на которой судят (`trivial_iou` = |истина| / |кадр|), плюс запас
  `live_iou_margin_over_trivial` из схемы. Метод, не перебивший его, не нашёл ничего: то же
  число даёт ответ, не смотрящий на пиксели вовсе;
- **потолок** — лучший синтетический домен (`max(SYNTHETIC_IOU)`). Живое обязано быть хуже по
  четырём названным причинам; если оно лучше лучшей синтетики, первое подозрение —
  загрязнение, а не успех.

**Сравнение доменно-сопоставленное.** `DOMAIN_FOR_KIND` объявляет, какому синтетическому
домену отвечает каждый вид записи. Запись браузера против `depth` — не сравнение, а разница
постановок.

**Ожидание откалибровано порчей картинки, а не подбором числа.** Четыре причины, по которым
живое обязано быть хуже, уже были названы словами; `tools/measure_live_penalty.py` наносит
каждую из них на синтетический кадр и прогоняет **тот же** `bench_domain` — порча входит
хуком `distort`, кадр портится, истина не портится. Хук в самом замере, а не копией цикла в
скрипте: копия разошлась бы, и падение от порчи смешалось бы с падением от расхождения двух
реализаций подсчёта.

**Публикация «IoU на синтетике» без единицы усреднения запрещена механически.** Проверяет
`test_iou_is_never_published_without_its_unit` по всем публикуемым файлам. Устный запрет здесь
уже был и не сработал: числа расходятся молча.

## Источники захвата (TASK-21)

### Источник — переключатель структуры, а не удобство

Захват окна выглядит настройкой производительности и ею не является. **Границы окна знает
операционная система, и захват окна отдаёт их агенту готовыми**: край кадра совпадает с
краем окна, обрамление приложения оказывается прибитым к рамке неподвижно и навсегда, а
рабочего стола за окном в поле зрения нет вовсе. Это половина задачи разделения экранного
и мирового слоя, выданная бесплатно и незаметно — в кадре не видно ничего лишнего, из него
**вырезано** лишнее.

Отсюда несравнимость чисел. IoU на записи окна отвечает на вопрос «отделяет ли метод
интерфейс приложения от его содержимого», на записи экрана — «отделяет ли он неподвижное
обрамление от движущегося мира, не зная, где кончается окно». Поэтому `capture_source`
объявлен `structural=True`: он меняет `structure_hash`, то есть форкает журнал, и
`corpus.live.mixed_sources` отказывается сводить записи разных источников в одну медиану.
Отказ стоит в `compare_to_synthetic` — там, где число и появляется, а не в стороне.

**Эпоха схемы и устройство опыта — два разных диагноза.** Записи, сделанные до появления
переключателя, его не содержат, и `structure_hash` у них расходится с новыми уже поэтому.
`mixed_sources` различает эти случаи: «разные эпохи схемы» с перечислением добавленных
позже настроек — не то же, что «различается другой структурный переключатель». Иначе первая
живая запись оператора после следующего структурного добавления получила бы отказ с
причиной, которой оператор не создавал. `capture_source` у старых записей выводится как
`display` (иного захвата тогда не было), и **вывод объявлен словами** в
`LiveScore.capture_source_from`: подставленный молча, он сделал бы запись увереннее, чем она
есть.

**Вид — в хеше, рамка — нет.** Координаты окна зависят от машины, монитора, масштабирования
и того, куда оператор подвинул окно мышью. Они описывают обстоятельства одной записи, а не
устройство эксперимента, поэтому живут в журнале записью об источниках (`code: source`,
вместе с тем, **откуда** рамка взялась) и не форкают журнал при каждом перетаскивании.

### Ввод уже кадра — решение, и у него два основания

Профиль по умолчанию: `capture_source: display`, `input_scope: window`. Снимаем весь экран,
действуем в одном окне. Основания:

1. **Кадр обязан содержать то, что видит человек.** Сузить захват до окна значит отнять
   контекст, который у человека есть, и вместе с ним выдать готовую рамку (см. выше).
2. **Ввод обязан быть уже кадра.** Инъекция в области `device` означает, что агент может
   нажать на что угодно на машине, включая окно исследователя и диалог подтверждения.

Из двух вместе выходит третье, и оно ценно: часть кадра меняется и не поддаётся влиянию. У
проекта для этого есть слово — **погода** (`devices.Device.is_weather`): её надо
предсказывать, изменить нельзя. Это обучающий сигнал, а не дефект постановки.

Обратное сочетание — снимать окно, а вводить шире — называется **невидимая рука** и
объявлено дефектным: последствие действия окажется за краем поля зрения, агент не заметит,
что натворил, и откатить не сможет. `capture.source.pairing` называет все сочетания, и
`harness record` печатает вывод до записи.

**Недосмотр в реализации был, и он найден замером.** `input_scope` читался в
`devices.Device.scope`, откуда попадал единственно в отчёт, а шлюз доставки спрашивал маску
про литерал `"window"` из подписи метода. Настройка выглядела работающей — детектор мёртвых
параметров считал её работающей, — и переключение на `device` не меняло ни одного исхода
доставки. Вреда не случилось по случайности: `window` — самая узкая из четырёх областей, то
есть литерал по недосмотру стоял на безопасной стороне. Теперь область приходит из профиля
(`Injector(profile=...)`), и **откуда она пришла**, пишется в журнал при каждой доставке
(`scope_from`): область по умолчанию и область, объявленная профилем, — разные условия опыта.

Это же обнажило слепое пятно детектора мёртвых параметров: чтение **в поле объекта**, чьи
потребители — только отчёты, он считает настоящим чтением. Инвариант 30 говорит «величина,
единственный потребитель которой печать отчёта, читателем не считается», но проверяется это
по функции, в которой стоит чтение, а не по судьбе значения.

### Захват области — рычаг бюджета, и он измерен

`harness cost --sizes --levels`, доля изменения полная (там, где бюджет и трещит),
синтетический рабочий стол, 20 кадров на точку, единица — кадр:

| Кадр | Пикселей | Стоимость | Дешевле | На кадр |
|---|---|---|---|---|
| 1920×1080 | 100 % | 100 % | 1.00× | 57.9 КиБ |
| 1280×720 | 44.4 % | 43.3 % | 2.31× | 26.1 КиБ |
| 960×540 | 25.0 % | 24.3 % | 4.11× | 14.7 КиБ |
| 640×360 | 11.1 % | 10.9 % | 9.16× | 6.8 КиБ |

Стоимость падает **по пикселям** — ни быстрее, ни медленнее. И главный ответ на гипотезу
задачи: уменьшить область дешевле, чем понизить уровень сжатия, причём по обеим величинам
сразу. Окно 960×540 на уровне 6 — 3.8× по времени и 3.9× по диску. Понижение уровня 6→1 на
полном кадре — 3.0× по времени и **плата диском**: 2.3× байт на кадр.

Оговорка про среду, без которой числа обманывают: время стадии «запись», снятое в
контейнере, к диску оператора отношения не имеет. Уровень 0 выходит здесь самым быстрым
(2.7 мс против 21.0 на уровне 6) именно поэтому — 2025 КиБ на кадр при 30 кадр/с это
59 МиБ/с непрерывной записи. Переносимы отношения между размерами и между уровнями, потому
что они про процессор.

### Отвергнуто: перехват буфера DirectX

Идея всплывает сама: подключиться к буферу кадра игры и получать картинку до вывода на
экран, дешевле и точнее. **Отвергнуто, и не из-за трудоёмкости** — два довода по существу
проекта:

1. **Кадр из буфера — это кадр, которого человек не видит.** В нём нет композитинга
   рабочего стола, оверлеев, курсора, уведомлений и артефактов вывода. Проект строится на
   том, что у агента ровно те же пиксели, что у человека, севшего за этот компьютер;
   картинка «чище человеческой» ломает это в корне, и все числа разделения себя и мира
   станут числами про другой мир. Заодно исчезает курсор — единственная часть кадра,
   строго следующая за действиями (см. ниже).
2. **Перехват требует внедрения в чужой процесс и ловится античитами.** Внедрение в процесс
   означает, что харнесс перестаёт быть наблюдателем и становится участником; античит
   означает блокировку и бан аккаунта оператора, то есть необратимое последствие вне
   эксперимента (`CONTACT.md`, подтверждаемая зона).

Что вместо: Desktop Duplication (dxcam) видит полноэкранные DirectX-приложения и отдаёт
именно то, что попало на экран. Этого достаточно, и это уже работает.

### Несколько экранов — одно поле зрения

Человек с двумя мониторами имеет одно поле зрения и **переводит взгляд**. Поэтому второй
дисплей заложен как направление внимания, а не как параллельный канал: `Registry.compose`
**отказывается** склеивать два видимых монитора в кадр двойной ширины, кадр берётся у
активного источника (`attention_frame`), а перевод взгляда — отдельное действие (`switch`),
которое пишется в журнал со своим `actor_layer`.

Причина не в эстетике. Склейка двух мониторов даёт агенту то, чего нет ни у одного
человека: одновременное наблюдение двух мест. С такой картинкой он никогда не выучит, что
взгляд надо переводить, что за пределами взгляда мир продолжает меняться и что об этом надо
помнить, — а это и есть содержание задачи о внимании.

Заодно исправлена конфабуляция в самом журнале: запись о переключении заявляла в теле
события слой того, кто вызвал, даже когда `device_switch_is_action: false` объявляла
инициатором человека. Расхождение заявленного и настоящего инициатора внутри одной записи —
ровно то, что метрика конфабуляции считает у планировщика; заводить его в журнале значит
портить прибор. Теперь слой в теле совпадает с записью, а то, что просил вызывающий,
записано отдельным полем `asked_layer`.

### Исчезновение источника — событие мира

У чтения источника **четыре** ответа, а не два: кадр, «кадр тот же» (`UNCHANGED`), «источник
исчез» (`GONE`) и «поток кончился» (`None`); поломка механизма — исключение `CaptureBroken`.
Исчезновение пишется наблюдением (`Kind.DEVICE`, `code: source_gone`), поломка — разрывом
(`Kind.CAPTURE_GAP`). Различать надо в обе стороны:

- исчезновение, записанное разрывом, учит агента разрыву, которого не было, и портит счёт
  целостности записи: разрыв означает «механизм не справился»;
- поломка, записанная исчезновением, прячет дефект захвата под видом события мира — искать
  его будут в поведении агента, а он в механизме.

`Actor.NONE` у исчезновения: окно закрыл человек вне эксперимента, монитор отключил кабель.
Приписать это оператору значило бы заявить инициатора, которого не наблюдали.

Переезд окна исчезновением не считается: `WindowFollowing` перепрашивает рамку каждый оборот
и снимает окно там, где оно теперь. «Снимаю окно» означает окно, а не прямоугольник, где
окно однажды было.

### Курсор остаётся в кадре

Курсор занимает 0.09 % кадра (7×7 пикселей на 320×180; на 1080p ещё меньше) и на IoU не
влияет измеримо — это показал замер порчи в TASK-11, часть 1: доля 1.000 при разбросе
0.981–1.063. Соблазн убрать его ради чистоты кадра поэтому реален, и **убирать нельзя**.

Курсор — единственная часть кадра, строго следующая за действиями агента. Это готовый
сигнал **реафферентации**: то, что движется одновременно с моим выходом и только с ним,
принадлежит мне. На нём стоит отделение себя от мира в самом дешёвом виде, доступном до
всякого обучения: движение мыши даёт мгновенную, локальную, стопроцентно
скоррелированную обратную связь, каких больше нет ни у одного действия. Убрать его — значит
отнять у классификатора `self` его первый и самый надёжный пример, и заметить это по IoU
будет нельзя: он от курсора не зависит.

## Прогон М4 по живому материалу и начало М5 (TASK-22)

### Опись объявлена до появления записей

`harness m4-live` прогоняет по живому корпусу то, что до сих пор шло только на синтетике:
разделение себя и мира, тождество карточек и **опись расхождений** — двенадцать проверок, у
каждой записано, что показала синтетика и какая у числа единица независимости.

Порядок здесь и есть смысл: список зафиксирован в коде **раньше**, чем появился первый живой
кадр. Замер, чей состав выбирают после того, как увидели данные, ничего не опровергает; и
пока записей нет, команда печатает всю опись вместе с отказом, а не молчит.

**Первый прогон — инвентаризация, а не починка.** Ни одно расхождение не исправляется в той
же задаче, где найдено: правка по первому найденному обычно ломает второе, а второго ещё
никто не видел. Код возврата от расхождений не зависит — иначе сценарий заставлял бы чинить
вслепую.

### Тождество на живых пикселях: третий источник отпечатка

Механика слияния и расщепления прогоняется третьим источником, где отпечаток приходит из
настоящих кадров (`m4live.LiveFingerprint`). Истина остаётся у исследователя, как в TASK-14.

**Встречи берутся из спокойного отрезка записи, и это не удобство.** Первая редакция брала
подряд идущие кадры любого отрезка и получила 33 карточки при шести сущностях. Число
выглядело результатом и им не было: на прокручивающемся экране фиксированная полоса — не одна
и та же вещь, её содержимое меняется целиком, и «шесть сущностей по восемь встреч» в такой
постановке просто ложь о мире. Замер был вакуумен по свойству постановки (инвариант 27).
Теперь встречи берутся там, где область действительно та же — на отрезке, где экран почти не
менялся, — а если такого отрезка в записи нет, ответ «нечем проверить», и это находка про
запись. На дизеринге ±1 уровень живой отпечаток даёт 14 карточек вместо шести, и пересмотр
сводит их обратно к шести: ошибка 8 → 0.

### М5: арена с мгновенным респавном

`behaviour.arena` — короткие сценарии с четырьмя исходами эпизода (цель достигнута, бюджет,
мир сломан, прервано). Три вещи, которые здесь легко испортить и которые проверены тестами:

- **мир не ставится на паузу**: респавн — такой же шаг мира, часы `t_world` идут через
  границу эпизода;
- **обе границы эпизода в журнале** — тайной перезагрузки не бывает;
- **возрождение — действие агента** (инвариант 17), и по умолчанию его инициатор
  `ActorLayer.DRIVE`, а не человек: решение «начать заново» приходит от драйва.

Порядок проверки исходов — цель, поломка, бюджет — тоже решение: обратный порядок записал бы
эпизод, где цель достигнута последним тиком, как «не успел», и данные о достижимости уехали
бы в пессимизм.

Награды в арене нет. Эпизод либо привёл туда, где тест цели проходит, либо нет; сравнивать
эпизоды можно по времени и по числу проб — величинам, которые кто-то измерял.

### М5: живой цикл, и что в нём измеримо

`harness live` крутит контуры против арены. Четыре условия вехи проверяются числами:

| Условие вехи | Как измерено | Результат |
|---|---|---|
| мир ни разу не остановлен | оборотов цикла = тиков мира, равенством | 11279 = 11279 |
| субсумпция работает | перебиваний нижним контуром верхнего | 317, не ноль |
| `actor_layer` заполняется | у каждого действия слой того контура, что ответил | 1670 из 1670 |
| конфабуляция считается | метрика по журналу, единица — эпизод | считается, но вырождена |

Планировщик здесь нарочно **длиннее среза** (400 шагов против `contour_max_yields` = 64):
при коротком поиске он успевает закончить внутри одного среза, субсумпция не срабатывает ни
разу, и «не сработало, потому что не понадобилось» становится неотличимо от «не работает»
(инвариант 26).

### Первый же прогон цикла нашёл вырождение метрики конфабуляции

Доля объяснений «не тем слоем» совпала с долей действий, начатых рефлексом, — до **0.12 п.п.**
на трёх отношениях частот (1:40, 1:4, 1:1; три сида каждое, единица — прогон, n = 9).

Предсказание инварианта 13 подтвердилось: доля следует за отношением частот, как и записано.
Но подтвердилось оно **вырожденной формой метрики**. Причина в постановке: объяснение
планировщика стоит до следующего объяснения и приписывается всем действиям подряд, поэтому
«объяснено не тем слоем» тождественно «начато не планировщиком», а это уже известно из
распределения по слоям. Выдавать 83.7 % за измеренную конфабуляцию нельзя — это доля рефлекса
под другим именем.

Чинится не порогом: ссылка на объяснение должна ставиться там, где планировщик считает, что
он и вызвал действие. Правка отложена намеренно — она в списке, а не в этой задаче.
Вырождение внесено в `MEASUREMENT.md`, раздел 13.5.

## Пакет TASK-24: ожидание исполнения, уровни, окна внимания

### Объяснение живёт, пока живёт ожидание исполнения

Правка, которую отложила TASK-22, сделана. Планировщик, выдав команду, заводит `Expectation`
на длительность самого действия (`livecycle.Expectation`: `reason_id`, `action`, `until_s`), и
`stated_reason_id` попадает в срез состояния **только пока ожидание живо**. Действия, которые
рефлекс успел сделать помимо, в знаменатель конфабуляции больше не входят.

Устройство важнее числа: ссылка на объяснение теперь привязана к тому, что планировщик
**считает** своим действием, а не к отрезку времени между двумя его репликами. Это разные
множества, и первое — то, о чём говорит инвариант 13.

Счётчики завелись вместе с механизмом, иначе ветку не отличить от неработающей:
`expectations`, `expectations_expired`, `under_expectation`, `expectation_kept`,
`expectation_usurped`. Разрыв с долей рефлекса вырос с 0.12 п.п. до 40.9 п.п.
(`MEASUREMENT.md`, 30.1).

### Уровни областей: `model/gauges.py`

Область — ячейка сетки поверх экранного слоя, и её имя (`AREA_3_5`) координат не несёт
(инвариант 4). Сегментации «настоящих» элементов интерфейса здесь нет намеренно: она была бы
догадкой о структуре, которой у агента нет, а сетка не привносит структуры вовсе.

Три решения, каждое из которых стоило прогона:

1. **Уровень считается только по пикселям экранного слоя.** Средняя по всей ячейке измеряет
   движение мира, просвечивающего сквозь ту же ячейку, и сигнал тонкой полоски в ней тонет.
2. **Устойчивость ячейки определяется положением**, а не тем, менялся ли уровень за прогрев.
   Критерий, зависящий от того, случилось ли за окно наблюдения искомое событие, отбрасывает
   искомое тем чаще, чем оно редкее.
3. **Окно корреляции включает тик самого события.** `deltas[i]` — изменение, наблюдаемое на
   тике `i+1`; событие на тике `t` оставляет главный след в `deltas[t-1]`.

Порог связи и минимальное число событий — в схеме (`link_min_effect`, `link_min_events`), то
есть в `profile_hash`, а не в коде анализа (инвариант 23). Оба объявлены на пути «агентский
стек» и только на нём: замер идёт по синтетическому миру, но истолковывает связь агентский
модуль, и путь замера читателем не делает — детектор мёртвых параметров поймал это как
однобокость.

Драйв делается **только из убывающей** связи. Растущая записывается, но драйвом не становится:
«растёт, когда я делаю X» — награда, а награды в проекте нет.

### Внимание: `perception/attention.py`

Бюджет — `attention_windows`, и до этой задачи он был единственной мёртвой осью модуляции из
семи. Теперь у оси есть читатель: `Attention.from_profile` берёт бюджет, `Attention.modulate`
принимает сужение настроением.

Два источника претензий не равны в правах, и асимметрия не вкусовая. Заметность (закрытый
набор признаков: резкое изменение, движение, звук вне поля зрения, всплеск ошибки предсказания)
имеет право перебить уже выданное окно и разрешения не спрашивает — это та же субсумпция, что
в контурах. Релевантность цели ждёт очереди. Заметность — про события, которые уже случились и
могут не повториться; релевантность — про то, что будет нужно и подождёт.

**Окно занято, пока наблюдение не окончено.** Освобождает его `report`, а не наступление
следующего такта. Первая редакция сбрасывала выданные окна каждый такт, и ветка перебивания
была из-за этого **недостижима**: перебивать в начале такта было нечего. Замер дал ноль
срабатываний на всех трёх бюджетах — дефект по инварианту 26, найденный числом, а не чтением.
У права перебивать есть цена: прерванное наблюдение не даёт ничего, и это отдельное число
(`cut_short`).

Отчёт по источнику, окно которого не занято, — **отказ**, а не ноль. Так бывает ровно в одном
случае: наблюдение прервали, а наблюдатель об этом не узнал. Тихо зачесть такой отчёт значило
бы приписать пользу прерванному наблюдению и стереть цену перебивания.

Контроль (раздача по порядку поступления) живёт полем `arbitrate` в боевом коде, а не
подменой метода в замере: контроль, живущий в измерительном скрипте, отличается от боевого
кода не только тем, чем задумано.

**Чего у внимания ещё нет.** Распределитель окон не подключён к живому циклу: претензии в
замере строит объявленный мир источников, а не восприятие, и `Attention` пока не вызывается
ни из `harness live`, ни из `agentside`. Механизм измерен, но контуром не стал — по той же
причине, по которой это не спрятано в отчёте: «модуль есть» и «модуль работает в цикле» —
разные утверждения, и первое уже один раз выдавалось за второе (мёртвая ось внимания). Из
этого же следует, что тест инварианта 12 модуля пока не задевает: он идёт от `harness.agentside`
по импортам, а туда внимание не импортируется. Отладочный поток модуль не импортирует вовсе.

## Каскад восприятия (SPEC-FULL, A3)

`perception/cascade.py`. Четыре ступени, каждая дороже предыдущей и реже её; каскад —
**гейт и учёт**, а не новый способ смотреть. Ступени 1–3 исполняют уже существующие
части: `ScreenLayer` и `NearLayer`, `MidLayer` и `FarLayer`, `PerceptionFirewall`.
Таблица «слой → ступень» объявлена явно (`LAYER_STAGE`), потому что уровни слоёв — это
порядок субсумпции, а не ступени каскада, и совпадение чисел там случайно.

### Отметка «без изменений» — данные, а не пропуск

До этой задачи `UNCHANGED` от источника доходил до журнала и **не доходил до
восприятия**: слои работали на кадре, которого не было. Теперь у ступени 0 два входа —
ответ источника (бесплатный, разность не считается) и разность на уменьшенной копии, —
и они считаются раздельно (`free` против `measured`): «нам сказали» и «мы проверили»
дают разную экономию, и смешивать их значило бы потерять, какой источник сколько даёт.

Сдвиг числа (инвариант 25): на одних и тех же 120 кадрах экранный слой обновился
**104 раза вместо 120**.

### Два «не обновился», и они считаются раздельно

`PerceptionStack` различает `skipped` (слою не пора по частоте) и `blocked` (каскад
запер ступень). Разные причины лечатся разным, и одно число на обе скрыло бы, какая
именно работает. Часы слоёв (`LayerClock`) на запертом кадре **не идут**: иначе после
минуты неподвижности всем «пора» разом.

### Порог ступени 3 не заводится заново

Он уже есть в группе «Файрвол» — `model_min_novelty`, `model_min_gap_cycles`, — и решает
по нему `AskGate`. Свои пороги каскада живут в группе «Каскад» и попадают в
`profile_hash` (инвариант 23). Второй порог о том же был бы двумя валютами вместо одной.

### Чем распределяется бюджет

**Сужение sigma на миллисекунду**, и считается оно предельным, а не средним: сужение
приписывается той ступени, до которой каскад на этом кадре дошёл. Это и есть вопрос
бюджета — «сколько купит проход на ступень глубже». Sigma каскад не считает сам: её
отдаёт `sigma_probe`, а без него величина равна `None`, а не нулю.

### Что замер сказал против ожидания

Три вещи, и все три меняют планы (`MEASUREMENT.md`, раздел 38):

1. **Цена с глубиной не растёт**: ступень 1 стоит 17.61 мс, ступень 2 — 1.47 мс.
   Дорогое стоит перед дешёвым, потому что 93.5 % цены слоёв — это арбитр экранного
   слоя. Пока ступень 1 не разделена на дешёвый поток и дорогой арбитр, гейт по ошибке
   предсказания запирает дешёвое и пропускает дорогое;
2. **Ступень 3 недостижима на четырёх доменах из пяти**: рабочий диапазон ошибки лежит
   ниже порога 0.35. Пункт 5 критерия запуска A4 формально выполнен и фактически
   вакуумен;
3. **Экономия гейта задаётся доменом, а не поведением агента**: 0.728 неизменившихся
   кадров на `game` против 0.008 на `document`, и доля бездействия почти ни при чём.

### Чего у каскада ещё нет

Он не подключён к живому циклу: `harness live` и `agentside` его не зовут — стек слоёв
и сам туда пока не подключён. Механизм измерен, контуром не стал, и это сказано здесь,
потому что «модуль есть» и «модуль работает в цикле» — разные утверждения, и первое уже
один раз выдавалось за второе (мёртвая ось внимания).

## Режим среды, архив следа, судимая цель (TASK-32)

### Режим среды решает, кто вправе отвечать

`perception/regime.py`: четыре признака, определяемые наблюдением, и таблица «механизм →
какие признаки ему нужны». Механизм без нужного признака докладывает **«неприменимо»** и
называет отсутствующий признак — числа не выдаёт. Исходов три: применимо, неприменимо, не
определено; «не определено» и «нет» ведут к разным решениям и потому не сливаются.

Требование механизма бывает отрицательным (`не мир идёт без меня`) и записывается в той же
таблице приставкой, а не зеркальным признаком: набор признаков закрыт, и удваивать его ради
отрицаний значило бы удваивать таблицу истины ни за что.

Гейт стоит в кросс-доменном замере: `parallax_iou` остаётся в записи всегда (оно нужно
исследователю), а в сводку идёт только там, где параллакс применим. Смешивать «плохо» и «не
о том» — та ошибка, из-за которой разброс 0.196–0.815 читался как качество метода.

### Вывоз следа — третья операция, а не разновидность удаления

`core/archive.py`. Понижение выбрасывает подробности и к нулевому уровню неприменимо; вывоз
сохраняет содержимое целиком и потому нулевому уровню доступен; удаления нет ни в какой
ветке. `Archive.forget()` существует ровно затем, чтобы попытка удалить упиралась в
объяснение, а не в `AttributeError`: второе читалось бы как «не дописали».

Причина вывоза обязательна, как у закладки. Содержимое сверяется по адресу **в обе стороны**:
при вывозе и при возврате. Недоступное холодное хранилище — не потерянный сегмент: горячий
индекс помнит, что он есть, сколько весит и по какому адресу.

### Органы: конкретные ресурсы вместо абстрактной загрузки

`core/organs.py`. Каждая величина с единицей и источником; непрочитанная возвращается как
`None` с названной причиной, и ноль запрещён конструктором. «Видеопамяти свободно 0» и
«видеопамять читать нечем» ведут к противоположным решениям, и подменять второе первым — та
самая молчаливая заглушка.

### Цель с внешним судьёй: предсказание не бывает результатом

`model/reflected.py`. Тест такой цели — предсказание чужой оценки, и это опасное место:
агент мог бы «выполнять» цели, предсказывая одобрение. Поэтому состояний два, и они не
сливаются: `predicted` годится для планирования и ни для чего больше, `settled` закрывает
цель. Пути «предсказал → выполнено» в коде нет, а не запрещён соглашением; `passed` при
отсутствии оценки равно `None`, а не `False`.

Мера пользы `ReflectedSelf` — **калибровка**, средний промах предсказания против полученной
оценки, единица независимости — оценка. Промах около 0.5 из 1.0 означает ответ наугад, и
модель обязана это признать числом (`better_than_nothing`). У этой проверки **три** исхода:
при разнице меньше стандартной ошибки среднего она отвечает «не отличимо от наугад», потому
что запаса ровно на границе 0.5 у неё нет, и без этого она объявляла победу шумом.

Оценка **без** предсказания закрывает цель наравне с любой другой: закрывает её ответ судьи,
а не согласие агента с ним. Промах при этом не записывается — его не существует, и разница
видна числом (`without_prediction`). Обратное правило было первой редакцией и оказалось
тупиком: предсказание берётся из `mu`, `mu` растёт из оценок, а оценки не принимались без
предсказания — канал не мог начаться.

## Цена ошибки, опорный уровень, канал оценки (TASK-33)

### Разведка читает цену ошибки, а не только полноту знания

`behaviour/babbling.py`. У лепета две величины вместо одной: полнота знания и `error_cost` —
цена ошибки. Она отделена от `Reversibility` по смыслу: обратимость **про мир** и не портится
неудачной догадкой, цена **про риск** и считает неудачные догадки тоже, потому что инвариант
9 определяет осторожность как «я не умею это откатить».

Три правила, каждое поставлено замером:

1. **Свои свидетельства сильнее умолчаний и флагов.** Фон тела — умолчание там, где своих
   свидетельств нет, и не пол над ними; найденный способ отката отменяет и прошлые неудачные
   догадки, и флаг «догадки кончились». Четыре дефекта подряд были нарушением именно этого.
2. **Цена решает «что раньше», но не «узнавать ли».** Ветвь «обратимость неизвестна» не
   пропускается никогда: она единственная, ради которой цену платят.
3. **Проба, которая ничему не научит, не стоит цены.** Выход, перестающий отвечать, уходит в
   хвост в обеих ветвях, где это важно; порог живучести — в схеме (`babble_stale_streak`).

Сравнение с порогом осторожности — одно на весь проект (`core.action.too_risky`) и строгое:
порог 1.0 означает «рискованным не считается ничего», и при нестрогом сравнении контроль
«порог снят» не снимал ничего. Ветви лепета считаются через `core.branches.Arbitration`
(инвариант 26).

### Опорный уровень домена: нет фона — нет ответа

`perception/regime.py`, `Baseline`. Опорный уровень — измеряемый объект с `n` и единицей, а не
число внутри сравнения, и у каждого признака в `Evidence.reference` сказано, с чем сравнивали.
Признак без записи неподвижности отвечает «не определено»: порог, снятый с другого домена,
был бы подсказкой об этом. Фон для обратимости снимается через тот же промежуток, что у самой
проверки, а отсчёт для «вид вернулся» объявлен структурной настройкой
(`regime_view_reference`), потому что от него зависит ответ признака.

### Канал оценки от оператора

`model/marks.py`. Отметка «получилось / частично / нет» после эпизода, с доверием к источнику,
через асинхронную очередь. Три границы: отметка не ставит цель и не порождает действие
(в модуле нет ни одной такой функции); источника «агент» не существует, и `behaviour/` этот
модуль не импортирует; цель закрывает ответ судьи, а не согласие агента с ним. Доверие весит
сдвиг ожидания и **не** весит промах — иначе агент улучшал бы свою калибровку, объявляя
неудобного судью недостоверным.

Судьи пока нет ни у одного домена, поэтому детектор режима объявляет такую цель
**неприменимой со статусом «не определено»**: механизм готов, мерить его нечем, и это
сказано числом покрытия (3 признака из 4), а не тишиной.
